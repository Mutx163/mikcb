本站是独立的 Next.js + Fumadocs 应用，产物为纯静态文件，不依赖 Node 运行时服务器。

## 本地开发

在仓库根目录进入 `site/`：

```bash
cd site
pnpm install
pnpm dev
```

开发服务器默认在 `http://localhost:3000`。修改 `content/docs/` 下的 MDX 后会热更新。

## 静态构建

```bash
cd site
pnpm build
```

`next.config.mjs` 已开启 `output: 'export'`，构建结果写入 `site/out/`。产物特点：

- 每个页面都有对应的 `.html` 与同名 `.txt`（纯文本，便于 AI agent 抓取）
- 全文搜索索引在 `out/api/search/`，浏览器端计算，无需服务端
- 可直接丢到任意静态托管（Cloudflare Pages、Nginx、GitHub Pages 等）

本地预览导出结果：

```bash
# 任意静态服务器即可，例如：
npx serve site/out
```

<Callout type="warn">
  Cloudflare Pages 构建时必须设置环境变量 `NODE_VERSION=22`。Fumadocs 要求 Node ≥ 22，而 Pages 默认 Node 版本偏低，不设会直接构建失败。
</Callout>

## 上线到 Cloudflare Pages

目标域名：`docs.163366.xyz`。

<Steps>
<Step>
在 Cloudflare Pages 中新建项目，连接 GitHub 仓库 `Mutx163/mikcb`。
</Step>
<Step>
配置构建：

| 项 | 值 |
| --- | --- |
| Root directory（根目录） | `site` |
| 构建命令 | `pnpm install --frozen-lockfile && pnpm build` |
| 输出目录 | `out` |
| 环境变量 `NODE_VERSION` | `22` |

**为什么 Root directory 必须是 `site`（2026-09-13 真实故障）**

原配置是「根目录留空（= 仓库根）+ 命令 `cd site && pnpm i && pnpm build`」，
在 Cloudflare 上直接失败：

```text
Executing user command: cd site && pnpm install && pnpm build
No preset version installed for command pnpm
Failed: Error while executing user command. Exited with error code: 126
```

原因：Cloudflare Pages v2 构建系统按**根目录**探测包管理器。仓库根既没有
`package.json` 也没有锁文件——`site/package.json` 里的
`"packageManager": "pnpm@11.22.0"` 与 `site/pnpm-lock.yaml` 都在 `site/` 下——
于是 CF 只装了 Node、**没有装 pnpm**，`pnpm` 命令不存在 → 退出码 126。
注意 `NODE_VERSION=22` 本身是生效的（日志里有 `Installing nodejs 22.22.0`），
失败点只在 pnpm。

把 Root directory 设为 `site` 后，CF 就地读到 `packageManager` 与
`pnpm-lock.yaml`，自动装上对应版本的 pnpm；构建命令也就不再需要 `cd site`。

> 若因故必须保留「根目录 = 仓库根」，则把构建命令改为
> `corepack enable && cd site && pnpm install --frozen-lockfile && pnpm build`，
> 由 corepack（Node 22 自带）依据 `packageManager` 提供 pnpm。

**已知问题：`__next.*` 预取载荷 404（Cloudflare Pages 路径匹配差异）**

Next.js 静态导出把 RSC 预取载荷落盘为带字面 `$` 的目录嵌套形式：

```text
site/out/docs/guide/quick-start/__next.docs/$oc$slug/__PAGE__.txt
```

而客户端预取请求用的是点号压平形式：

```text
GET /docs/guide/quick-start/__next.docs.$oc$slug.__PAGE__.txt
```

`site/public/_redirects` 把点号形式以 200 重写到嵌套形式。

> ⚠️ **这条规则的前提尚未确认，部署后必须复测。**
> 2026-09-13 在线上（当时仍是旧构建、`_redirects` 未上线）实测：**两种形式
> 都返回 404** —— 既复现不出「嵌套 200」，也复现不出「点号 404」。既然前提
> 对不上，就不能假设重写一定有益：若目标路径不存在，200 重写反而会把一个
> 本来可用的 URL 变成 404。另外该规则的通配符 `/docs/*/…` 覆盖不到
> `docs/__next.docs.$oc$slug/__PAGE__.txt`（中间没有路径段），`_not-found`
> 也没有规则；规则里还硬编码了 Next 内部段名（`$oc$slug`、`!KGhvbWUp`），
> 升级 Next 会静默失效。
>
> 复测方法（部署后逐条 `curl -sI`）：`/docs/guide/quick-start/__next.docs.$oc$slug.__PAGE__.txt`
> 与 `/docs/guide/quick-start/__next.docs/$oc$slug/__PAGE__.txt`，确认前者由
> 404 变 200 且后者仍可用。本地可用
> `python3 -m http.server --directory site/out` 对比两条路径。
</Step>
<Step>
部署完成后，在 Pages 项目的自定义域中添加 `docs.163366.xyz`，按提示完成 DNS。
</Step>
</Steps>

之后主分支上对 `site/` 的推送会自动触发重新构建与发布。

## 上线检查清单（换域名 / 长期间未部署后逐条核对）

2026-09 换域名（`mutx.ccwu.cc` → `163366.xyz`）时踩过的坑，逐条对应一个真实故障：

| 检查项 | 怎么查 | 出现过的问题 |
| --- | --- | --- |
| 文档站是否真的重新构建过 | `curl -s https://docs.163366.xyz/ \| grep canonical` | 源码已加 canonical/sitemap/llms.txt，但 Pages 仍是旧构建，全部 404 |
| 文档站 sitemap 可达 | `curl -sI https://docs.163366.xyz/sitemap.xml` | 构建过期时为 404，24 篇文档页对搜索引擎零入口 |
| 旧域名 301 是否一步到 https | `curl -sI https://mutx.ccwu.cc/ \| grep -i location` | 曾一度跳到 `http://163366.xyz/`（明文中间跳），应为 `https://` 直达 |
| `www` 是否解析 | `getent hosts www.163366.xyz` | 无记录（NXDOMAIN）。若 GSC 属性建在 `www` 上，站点地图永远读不到 |
| 站点地图能否被读 | `curl -s https://163366.xyz/sitemap.xml \| python3 -c 'import xml.dom.minidom,sys;xml.dom.minidom.parseString(sys.stdin.read());print("ok")'` | 文件本身一直合法，问题在 GSC 侧属性状态 |

**换域名后必做**：GSC 里对应重新验证属性（旧验证随域名失效）、重新提交站点地图、
核对属性是「网域」还是「网址前缀」且与 301 目标一致。

## 维护本站时的已知坑

改这个站之前建议先读一遍，都是实际踩过的：

1. **`fumadocs-mdx` 15 生成的 `.source/` 没有 `index.ts`**  
   从 `@/.source/server` 导入，不要写 `@/.source`。

2. **MDX 里的裸 `<` 会被当成 JSX 标签**  
   例如版本区间 `>=3.12.2 <4.0.0`，`<4.0.0` 要用反引号包住，或改写为 `&lt;`。

3. **`Step` / `Steps` 不在默认 MDX 组件里**  
   已在根目录 `mdx-components.tsx` 手动注册；新增同类组件时同样要挂进去。

4. **pnpm 11 默认不跑依赖的构建脚本**  
   `esbuild` 等需要构建产物的包，已在 `pnpm-workspace.yaml` 的 `allowBuilds` 中放行。新增需要 postinstall 的依赖时同步更新该文件。

5. **`.source/`、`.next/`、`out/` 不要提交**  
   已由 `site/.gitignore` 排除；`out/` 由 Cloudflare 在构建机上生成。

6. **`app/favicon.ico` 会覆盖 `public/favicon.ico`**  
   Next 把 `app/favicon.ico` 当作**文件约定**（等价于一条 `/favicon.ico` 路由），
   路由优先于 `public/` 静态文件。2026-09-12 曾在 `public/` 下新增一份
   `favicon.ico`，它从未被服务过（`out/favicon.ico` 始终等于 `app/favicon.ico`）。
   要换图标请改 `app/favicon.ico`；`public/` 下只放不被 app 约定接管的资源
   （`favicon-48.png` 这类带尺寸的 PNG 不受影响）。
