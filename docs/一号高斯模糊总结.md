## 2. 我们在做什么效果

HyperOS / MIUI 设置页标题栏的典型观感：**列表从栏下滚过，栏后内容是实时变化的毛玻璃**。

mikcb 采用的是 **CFH 快照模糊**，不是实时 `BackdropFilter`：

```
RepaintBoundary 截屏（0.72x）
    → 按 scrollDelta 裁标题条带（含 18px bleed）
    → 铺不透明底色（防黑边）
    → 高斯模糊（Android 原生 RenderEffect / Dart ImageFilter）
    → RawImage 贴回标题栏 + tint 半透明蒙层
```

### 2.1 哪些页面会真模糊

| 页面 | `overlayHeader` | 实际效果 |
|------|-----------------|----------|
| 设置首页（`TimetableSettingsScreen`） | `true` | 完整 CFH |
| 课表首页（`TimetableScreen`） | `false` | 仅 tint，不截图 |
| 子页面（`HyperosSubpage` 默认） | `false` | 仅 tint |
| iOS / Web | — | 仅 tint（产品范围） |

门控：`_cfhCaptureEnabled = overlay && route 已 settle && Android`。

### 2.2 实现质量结论（算法层面）

**链路本身是对的**，常见坑已处理：

- 降采样 `headerPixelRatio = 0.72` 换性能；
- sigma 按倍率换算：`sigmaPx = 10.0 × 0.72 ≈ 7.2px`，显示拉伸后约 10 logical px；
- 模糊前铺 `scaffoldBackground`，避免透明像素糊成黑晕；
- `headerStripBleed` 给 kernel 留边，裁回可见高度；
- `blurGeneration` 防异步竞态；
- Android API 31+ 原生 blur，以下走 Dart `ImageFilter.blur`。

**它不是 bug 级的「写错了高斯公式」**，而是**交互策略 + 显示优先级**导致体感差。

## 3. 为什么不跟手：根因拆解

用户体感：**手指在滑时标题栏像贴了一张旧图，松手后才跳变**。  
这不是单一参数问题，而是四层叠加。

### 3.1 主因：preview 算出来了，但没显示

```dart
// frosted_header_controller.dart
ui.Image? get displayImage => _blurredImage ?? _previewImage;
```

滚动时后台已经 `crop` 出新条带并 `_applyPreview(strip)`，但只要上一帧 `_blurredImage` 还在，**UI 仍画旧模糊图**。  
轻量的裁条带跟手路径存在，但被 `??` 优先级挡死。

### 3.2 次因：滚动中还在做重 blur，且任务互相取消

单次 blur：`toByteData(RGBA)` → Platform Channel → 原生/Dart 模糊 → 拼回 `ui.Image`，常需 **50–200ms+**。

快速滑动时每次 crop 都 `++_blurGeneration`，在途 blur 全部作废，`_blurredImage` 长期不更新 → 画面冻在滑动前。

### 3.3 次因：停手后才刻意全量刷新

`ScrollEnd` → **200ms** debounce → `scheduleFullRefresh(forceFullCapture: true)`。  
这会强化「滑的时候不动，松手才变」。

### 3.4 加剧因素

| 因素 | 说明 |
|------|------|
| 16ms 节流写在 crop **完成之后** | 实际更新频率低于 60fps |
| 全屏 `toImage` 锁 | `_isCapturingSnapshot` 期间整段 `return`，crop 也停 |
| lazy ListView | 新条目进视野必须全屏重采；140ms 节流内 crop 偏移无效 |
| CFH 本质 | 离线位图模糊，不可能像 BackdropFilter 每帧真跟背景 |

### 3.5 因果链（一图看懂）

```
手指滑动
  → crop 出新 preview（快）
  → displayImage 仍返回旧 blurred（慢）     ← 用户看到「不动」
  → 同时发起 blur（慢）又被 generation 取消
  → ScrollEnd + 200ms idle
  → 全屏重采 + blur 终于完成               ← 用户看到「松手才变」
```

## 4. 方案全景对比

| 方案 | 跟手性 | 性能 | 成本 | 接近 HyperOS | 结论 |
|------|--------|------|------|--------------|------|
| **A. 实时 `BackdropFilter`** | 最好 | 差，列表易掉帧 | 低 | 高 | ❌ 不作主方案 |
| **B. 只调 sigma / 节流** | 差 | 中 | 极低 | 中 | ❌ preview 仍被挡，不治本 |
| **C. 只改 `displayImage` 优先级** | 明显改善 | 中 | 低 | 中高 | ✅ 必要，但不完整 |
| **D. 两阶段 CFH（滚动 crop、停手 blur）** | 好 | 好 | 中 | 高 | ✅ **最合适** |
| **E. 滚动也 blur，降 sigma** | 中 | 偏差 | 中 | 中 | △ 可作补充，不能单独依赖 |
| **F. 原生实时模糊（Surface / 系统 API）** | 最好 | 视平台 | 很高 | 最高 | ⏳ 长期方向 |

## 5. 最合适方案：两阶段 CFH

### 5.1 一句话

> **滚动时跟内容（只 crop + preview），停手后跟质感（全采 + 单次 blur）。**

把「位置同步」和「模糊质感」拆开，用不同成本的手段完成——这是在本项目约束下**性价比最高、风险最低**的路线。

### 5.2 两阶段行为

| 阶段 | 用户看到 | 后台做什么 | 是否 blur |
|------|----------|------------|-----------|
| **滚动中** | 条带内容随手指移动（可略锐） | 缓存 snapshot + `scrollDelta` crop | **否** |
| **停手后** | 过渡到毛玻璃 | 全屏重采（如需）+ **一次** blur | **是** |
| **静止** | 稳定毛玻璃 | 沿用 `_blurredImage` | **是** |

这与 HyperOS「滑时透、停时糊」的体感一致，也避免用 50–200ms 的 blur 去追 60fps 滚动这种不可能任务。

### 5.3 核心代码改动（概念）

**① 增加滚动状态**

`ScrollStart` → `_isUserScrolling = true`  
`ScrollEnd` + 短 debounce → `false`

**② 改显示优先级**

```dart
ui.Image? get displayImage {
  if (_isUserScrolling) {
    return _previewImage ?? _blurredImage;  // 滚动：preview 优先
  }
  return _blurredImage ?? _previewImage;    // 静止：blur 优先
}

bool get isPreviewActive =>
    _isUserScrolling || (_blurredImage == null && _previewImage != null);
```

滚动中继续用现有 `previewTintBoost` 遮住未模糊的略锐感。

**③ 改调度：滚动不 blur，停手再 blur**

| 事件 | 动作 |
|------|------|
| `ScrollUpdate` / `ScrollStart` | crop → `_applyPreview` → `notifyListeners`；**不调用** `_blurStripAsync` |
| 需全屏重采 | 排队即可，**不阻塞** crop-only 路径 |
| `ScrollEnd` | debounce **80–120ms**（可从 200ms 缩短）→ 按需 full capture → **单次** blur |

### 5.4 为何不是别的方案

| 备选 | 不选的原因 |
|------|------------|
| 维持现状 + 调参 | `displayImage` 逻辑 bug 仍在，preview 继续被挡 |
| 滚动中每帧 blur | 当前冻帧问题的根源；CPU/GC/Channel 扛不住 |
| 全页 BackdropFilter | 设置首页 ListView 重，掉帧风险大 |
| 推翻 CFH 换原生实时 | 工期高、与 Flutter 合成复杂，非本期目标 |

### 5.5 参数建议

| 参数 | 现值 | 建议 | 说明 |
|------|------|------|------|
| `_scrollUpdateThrottle` | 16ms | 保持 | crop 目标 ~60fps |
| `_scrollFullThrottle` | 140ms | 100–140ms | 全屏重采别太频 |
| `_idleDebounce` | 200ms | **80–120ms** | 停手后更快进入精修 |
| `headerPixelRatio` | 0.72 | 0.72–0.85 | 停手 blur 可略提清晰度 |
| `headerStripBleed` | 18 | 18–24 | blur 边缘不露硬边 |
| `previewTintBoost` | 0.12 | 保持或略增 | 遮滚动中锐图 |

可在 `DebugTuningPanel` 暴露上述项便于真机调参。

### 5.6 明确不做的事

- ❌ 滚动中每帧 blur  
- ❌ 只调 sigma/节流不改显示优先级  
- ❌ 设置列表改全屏 `BackdropFilter`  
- ❌ 去掉停手后全屏重采（lazy 列表会露馅）

## 6. 实施优先级

### P0 — 解决不跟手（必做）

1. `FrostedHeaderController` 增加 `_isUserScrolling`
2. 修改 `displayImage` / `isPreviewActive`
3. 滚动路径：crop + preview only，跳过 `_blurStripAsync`
4. 停手路径：debounce 后单次 full capture（按需）+ blur

### P1 — 减少卡顿

1. 全屏 capture 锁期间仍允许 crop-only（不要整段 `return`）
2. 合并 `hyperos_page` 与 `HyperosListView` 重复的 `ScrollNotification` 监听
3. `_pendingUpdate` 在滚动结束时 flush，不依赖 blur 完成回调

### P2 — 测试与可观测

1. 单测：scrolling / idle 下 `displayImage` 优先级
2. 单测：滚动中不 blur、停手触发一次 blur
3. Debug 输出：`mode=scroll_preview | idle_blur`、`blurEngine`、帧间隔

详细 checkbox 见 [3号高斯模糊总结](./3号高斯模糊总结.md) §6。

## 7. 验收标准（真机 · 设置首页）

1. **跟手**：慢滑时标题栏背后内容 **1–2 帧内**随列表移动（允许略锐、无 blur）
2. **停手精修**：松手后 **120ms 内**过渡到模糊 + tint，无突兀跳变
3. **快滑**：flick 时不应长期冻在滑动前的模糊帧
4. **lazy 列表**：新 section 滚入标题区，停手后内容与模糊一致
5. **性能**：滚动无明显掉帧
6. **回归**：子页、课表页、路由转场 tint-only 不变

## 8. 长期演进（非本期）

- Android 12+ 标题栏区域原生实时 blur（需评估 Flutter 纹理合成）
- 滚动 preview 用 GPU 轻量 box-blur（比 RGBA 往返轻，比 BackdropFilter 可控）

本期以**两阶段 CFH**落地即可。

## 10. 最终结论

| 问题 | 结论 |
|------|------|
| 高斯模糊写得对不对？ | **算法与 CFH 架构正确**；问题在交互策略，不在公式 |
| 为什么不跟手？ | **旧 blurred 挡住新 preview** + 滚动中重 blur 追不上 + 停手才全量刷新 |
| 最合适方案？ | **两阶段 CFH：滚动只 crop/preview，停手再 blur** |

这是在本项目（Flutter + Android 重列表 + HyperOS 观感）约束下，**跟手性、性能、实现成本、可维护性**平衡最好的方案。
