# 3号高斯模糊总结

> 范围：HyperOS 标题栏 CFH（Content Frost Header）毛玻璃效果  
> 相关代码：`lib/ui/hyperos/frosted/`、`lib/services/frosted_blur_service.dart`、`lib/ui/hyperos/hyperos_page.dart`  
> 日期：2026-07-06

---

## 1. 我们在解决什么问题

设置首页等 `overlayHeader: true` 的页面，标题栏需要呈现「内容从栏下滚过、背后实时毛玻璃」的 HyperOS 观感。

当前实现**不是**实时 `BackdropFilter`，而是 **CFH 快照模糊**：

```
RepaintBoundary 截屏 → 裁标题条带 → 高斯模糊 → 贴回标题栏 + tint 蒙层
```

架构方向正确（Flutter 下比全屏 BackdropFilter 更可控），但体感问题是：

- **滑动时不跟手**，标题栏像贴着一张旧图；
- **松手后才明显变化**，有时还有一次跳变。

---

## 2. 现状速览

| 项目 | 当前值 / 行为 |
|------|----------------|
| 生效页面 | `overlayHeader: true`（如设置首页） |
| 平台 | Android 有 live blur；iOS / Web 仅 tint |
| 截屏倍率 | `headerPixelRatio = 0.72` |
| 逻辑 blur sigma | `10.0`（物理约 `7.2px`） |
| 滚动节流 | 16ms 发起更新 |
| 全屏重采节流 | 140ms |
| 停手后 idle | 200ms debounce → 全屏重采 + blur |
| 显示优先级 | `_blurredImage ?? _previewImage` |

---

## 3. 不跟手的根因（按影响排序）

### 3.1 主因：滚动时 preview 被旧模糊帧挡住

```dart
ui.Image? get displayImage => _blurredImage ?? _previewImage;
```

滚动过程中后台已经裁出新条带并 `_applyPreview(strip)`，但只要上一帧的 `_blurredImage` 还在，**UI 仍显示旧模糊图**。  
轻量的「裁条带跟手」路径存在，但**没有被展示出来**。

### 3.2 模糊是重操作，快滑追不上

单次路径：`crop (toImage)` → Native RGBA blur / Dart `ImageFilter.blur`，常需 **50–200ms+**。  
快速滑动时 `_blurGeneration` 递增，进行中的 blur 任务被丢弃，画面长期停在滑动前的帧。

### 3.3 停手后刻意触发全量刷新

`ScrollEnd` → 200ms → `scheduleFullRefresh(forceFullCapture: true)`。  
这会强化「滑的时候不动，松手才变」的感受。

### 3.4 其他加剧因素

- 16ms 节流基于 `_lastPreviewAt`（crop **完成后**才写入），实际更新频率低于 60fps；
- 全屏 `toImage` 期间 `_isCapturingSnapshot` 锁会直接跳过更新；
- lazy `ListView` 新条目进视野需全屏重采，140ms 节流内 crop 偏移无法反映新内容。

## 4. 方案对比

| 方案 | 跟手性 | 性能 | 实现成本 | 观感接近 HyperOS | 结论 |
|------|--------|------|----------|------------------|------|
| A. 实时 `BackdropFilter` | 最好 | 差（每帧 GPU 采样） | 低 | 高 | ❌ 列表页易掉帧，不推荐作主方案 |
| B. 维持现状，只调 sigma / 节流参数 | 差 | 中 | 极低 | 中 | ❌ 不治本，preview 仍被挡住 |
| C. 修 `displayImage` 优先级（滚动也用 preview） | 明显改善 | 中 | 低 | 中高 | ✅ 必要，但不够 |
| D. **滚动期只 crop、停手再 blur（推荐主策略）** | 好 | 好 | 中 | 高 | ✅ **最合适** |
| E. 滚动也用 blur，但降 sigma / 降采样 | 中 | 中偏差 | 中 | 中 | △ 可作 D 的补充，不能单独依赖 |
| F. 平台原生实时模糊（SurfaceView / 系统 API） | 最好 | 取决于原生 | 很高 | 最高 | ⏳ 长期方向，短期不现实 |

---

## 5. 推荐方案：两阶段 CFH（滚动跟手 + 停手精修）

### 5.1 核心原则

> **滚动时跟内容，停手后再跟质感。**

把「位置同步」和「模糊质感」拆成两条路径，用不同成本的手段完成：

| 阶段 | 目标 | 手段 | 是否 blur |
|------|------|------|-----------|
| 滚动中 | 条带内容与手指同步 | 缓存 snapshot + `scrollDelta` 裁条带 | **否**（只显示 preview） |
| 滚动停稳 | 恢复毛玻璃质感 | 全屏重采（如需）+ 一次 blur | **是** |
| 静止 | 保持清晰模糊 | 沿用现有 `_blurredImage` | **是** |

### 5.2 显示逻辑（关键改动）

引入 `_isUserScrolling`（`ScrollStart` → true，`ScrollEnd` + 短 debounce → false）：

```dart
ui.Image? get displayImage {
  if (_isUserScrolling) {
    return _previewImage ?? _blurredImage;  // 滚动：preview 优先
  }
  return _blurredImage ?? _previewImage;    // 静止：blur 优先
}

bool get isPreviewActive =>
    _isUserScrolling || (_blurredImage == null && _previewImage != null);
```

滚动中可继续用现有 `previewTintBoost` 遮住未模糊的「略锐」感。

### 5.3 调度逻辑（关键改动）

**滚动中（`ScrollUpdate` / `ScrollStart`）：**

1. 仅走 `_rawFull` + `cropHeaderStripFromSnapshot(scrollDelta)`；
2. `_applyPreview(strip)` + `notifyListeners()`；
3. **不调用** `_blurStripAsync`（或 generation 取消所有在途 blur）；
4. 全屏重采：仅在 `_needsFullRecaptureForScrollDelta()` 为 true 且未命中 140ms 节流时排队，**不阻塞 crop**。

**滚动结束（`ScrollEnd`）：**

1. debounce **80–120ms**（可从 200ms 缩短，见 5.5）；
2. 一次 `forceFullCapture`（lazy 列表补帧）；
3. crop → **单次** `_blurStripAsync` → 写回 `_blurredImage`；
4. `_isUserScrolling = false`，切回 blur 优先显示。

### 5.4 为何这是「最合适」

1. **跟手**：crop 是轻量 `drawImageRect` + `toImage`，比 blur 快一个数量级，16ms 节流才有意义；
2. **性能**：滚动时不做 Native RGBA 往返，CPU/GC 压力显著下降；
3. **观感**：停手后一次 blur 与 HyperOS「滑时透、停时糊」一致；
4. **改动面小**：主要动 `FrostedHeaderController`，不必推翻 `FrostedCapture` / `FrostedBlurService`；
5. **风险可控**：子页 `overlayHeader: false`、iOS tint-only 路径不受影响。

### 5.5 参数建议（可在 Debug Tuning 暴露）

| 参数 | 现值 | 建议 | 说明 |
|------|------|------|------|
| `_scrollUpdateThrottle` | 16ms | 保持 16ms | 滚动 crop 目标 ~60fps |
| `_scrollFullThrottle` | 140ms | 100–140ms | 全屏重采不要太频 |
| `_idleDebounce` | 200ms | **80–120ms** | 停手后更快进入精修 blur |
| `headerPixelRatio` | 0.72 | 0.72–0.85 | 停手 blur 可略提清晰度 |
| `headerStripBleed` | 18 | 18–24 | 保证 blur 边缘不露硬边 |
| 滚动中 tint | `previewTintBoost` | 保持或略增 | 掩盖 sharp preview |

### 5.6 不建议做的事

- ❌ 滚动中每帧都 blur（当前问题的根源之一）；
- ❌ 仅靠调大 sigma / 缩短节流而不改显示优先级；
- ❌ 全列表页改用 `BackdropFilter`；
- ❌ 去掉停手后的全屏重采（lazy 列表会露馅）。

## 7. 验收标准

在设置首页（`overlayHeader: true`、Android 真机）：

1. **跟手**：慢速滑动时，标题栏背后内容应在 **1–2 帧内**随列表移动（允许略锐、无 blur）；
2. **停手精修**：松手后 **120ms 内**过渡到模糊 + tint，无明显「跳一张完全不同的图」；
3. **快滑**：快速 flick 时不应长期冻结在滑动前的模糊帧；
4. **lazy 列表**：新 section 滚入标题栏区域，停手后内容与模糊一致；
5. **性能**：滚动时无明显掉帧（不以「每帧 blur」为代价换跟手）；
6. **回归**：子页（`overlayHeader: false`）、课表页、路由转场 tint-only 行为不变。

---

## 8. 长期演进（非本期）

若后续要更接近系统级效果，可考虑：

- Android 12+ 对标题栏区域使用原生实时 blur（需评估与 Flutter 纹理合成）；
- 滚动 preview 用 GPU shader 做轻量 box-blur（比 RGBA 往返轻，比 BackdropFilter 可控）。

**本期不展开**；两阶段 CFH 是性价比最高的落地路径。

---

## 9. 一句话结论

**最合适方案 = 滚动期只裁条带、preview 优先显示（不 blur）；停手后全采 + 单次 blur 恢复质感。**  
这既修复了 `displayImage` 挡住 preview 的逻辑 bug，又从架构上避免「用重 blur 追 60fps 滚动」的不可能任务。
