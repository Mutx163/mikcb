## 2. 用户自测包怎么出

### 2.0 顺序（不可颠倒）

**收口 → 门禁绿（L1/L2）→ 提交 → 再出包 → 用户装**。包必须从已提交的 HEAD 出，且包含 R8 两行与 keep 规则。

### 2.1 用哪个变体

`prodRelease` —— 唯一「同包名 + 同签名 + release 档优化」的变体（release 块 `android/app/build.gradle:175-196`；白名单 `:250`）。

不要用：

- `prodDebug`：debug 签名 + 正式包名，和手机上的正式版撞签名，装不上（`:245-246`）；
- `prodBench`：白名单外，已关（`:250`）；
- `perfBench`：`.profile` 包名，数据是空的，测不出升级问题；
- **不要从 Android Studio 拷 APK**：AGP 会给它注入 `android:testOnly="true"`，普通安装会被系统拒（2026-11-09 在 AS 产物上实测）。AS 里点 Run 也不要用。

### 2.2 命令（PowerShell）

```powershell
cd C:\cursor\mikcb\android
.\gradlew.bat :app:assembleProdRelease -POVERRIDE_VERSION_NAME=3.0.0
```

- `-POVERRIDE_VERSION_NAME=3.0.0` 让 versionName 与 CI 出包一致（CI 用 tag 覆盖，`android-build.yml:195-202`；工程侧读取在 `android/app/build.gradle:38`）；不加会是 `3.0.0-0`。versionCode 恒 `100150`。
- 签名自动读 `android/key.properties`（四键齐全，`storeFile=app/upload-keystore.jks` 文件在；该文件被 `android/.gitignore:9` 忽略），不用环境变量。
- 这次会跑 R8，耗时比之前长，属正常。

### 2.3 产物与自检

产物：`C:\cursor\mikcb\build\app\outputs\apk\prod\release\app-prod-release.apk`（`android/build.gradle:28,34` 把产物统一到仓库根 `build/`）。应 > 5 MB（历史 v2.1.4.1 包 46,071,385 B）。

装前两条必查：

```powershell
$bt = 'D:\Cache\Android\Sdk\build-tools\36.0.0'   # 见 android/local.properties:1 的 sdk.dir
$apk = 'build\app\outputs\apk\prod\release\app-prod-release.apk'

# 1) 版本号与 testOnly
& "$bt\aapt2.exe" dump badging $apk | Select-String 'versionCode|versionName|minSdk'
& "$bt\aapt2.exe" dump xmltree $apk --file AndroidManifest.xml | Select-String 'testOnly'

# 2) 签名（必须与已发布 v2.1.4.1 同一把钥匙）
& "$bt\apksigner.bat" verify --print-certs $apk
```

预期：`versionCode=100150`、`versionName=3.0.0`、`minSdkVersion='33'`、`testOnly` **无输出**；证书 SHA-256 与 v2.1.4.1 一致（成员六 2026-11-09 已核：`995892a3…41e79ce` 相同）。不一致就别装——会 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。

（本机 SDK 在 `D:\Cache\Android\Sdk`（`android/local.properties:1` 的 `sdk.dir`）；build-tools 有 35.0.0 / 36.0.0 两套，用 36.0.0。换机器时先 `Get-ChildItem <sdk>\build-tools` 找版本号。）

### 2.4 覆盖安装注意

- 包名同为 `com.mutx163.qingyu`；新 versionCode `100150` > 已发布 `100140`（v2.1.4.1 的 `2.1.4-1+140` + 100000）→ 直接覆盖升级，**数据保留**。
- **装前先做一次应用内备份**（万一要回滚，卸载会清数据）。

- 桌面小组件 10 类、通知渠道、闹钟接收器兼容（成员十五 2026-11-09 核对）。

### 2.5 出问题怎么退回旧包

1. **装不上**（签名/降级冲突）：先别卸载，按 2.3 的证书指纹核对；确认冲突只能卸载重装（数据靠备份恢复）。
2. **装上后不可用**：卸载 → 装回官方 v2.1.4.1：`https://github.com/Mutx163/mikcb/releases/download/v2.1.4.1/mikcb-2.1.4.1-arm64-v8a.apk` → 从备份恢复。
3. **想保数据降级**（由用户本人执行；Agent 不碰 adb/真机）：`adb install -r -d mikcb-2.1.4.1-arm64-v8a.apk`。跨架构（Compose→Flutter）降级后数据格式未必兼容，仍建议先备份。
4. **自测包本身坏了**（R8 误删/崩溃）：这是发布阻塞，直接报 Chief；不要绕过门禁。

## 3. 发布当天命令清单（按顺序，不许并行）

> 全程一个人串行执行；禁止 force push；禁止手工 `gh release create` 补空资产。

### 阶段 A：合 main、推 main、等 CI 绿

**A0 收口确认**

```bash
git status --short        # 期望：空
git log -1 --oneline      # 记录本次 HEAD
```

失败：有脏文件就别往下走。

**A1 取远端**

```bash
git fetch origin
```

预期：`origin/main` 更新。失败：重试一次；仍失败停。

**A2 把 origin/main 合进 compose-merge**

```bash
git switch compose-merge
git merge origin/main
```

预期：`Merge made by the 'ort' strategy.`，无冲突（已核文件级 0 重叠）。
失败：`git merge --abort`，报 Chief；不要自己动冲突文件。

**A3 让本地 main 快进到 compose-merge**

```bash
git switch main
git merge --ff-only compose-merge
```

预期：`Fast-forward`（main 是 compose-merge 的祖先，已核）。
失败：**先停、报 Chief**，不要强推。原退路 `git push origin compose-merge:main` 会跳过 A4/A7 自检，只能经 Chief 同意、且 A4 已通过后，在 A5 阶段改用它（见 A5 注）。

**A4 版本 / 日志自检**

```bash
bash tool/verify_release_version.sh prerelease    # 正式版用 release
python tool/check_release_highlights.py
```

预期：`OK: versionName=3.0.0-0 versionCodeBase=150`；第二条 exit 0 并打印「本次重点」3 条全部认回条目。
失败：别打 tag。正式版却要求含 `-`，说明 version.properties 还没改。

**A5 推 main（同时推 GitHub 与 CNB）**

```bash
git push origin main
```

预期两行：GitHub `main -> main`、CNB `main -> main`。
失败：

- 被拒（non-fast-forward）→ `git fetch origin && git merge origin/main` 再推，**禁止 force**；
- CNB 那行报错但 GitHub 已成功 → `git ls-remote --heads origin main` 确认 GitHub 已更新，再 `git push cnb main` 补推 CNB，别重推 GitHub；
- 若 A3 无法快进（经 Chief 同意）：把本步命令换成 `git push origin compose-merge:main`（**A4 必须先通过**），推送后再把本地 `main` 对齐到 `compose-merge` 即可继续。

**A6 等 main CI 变绿**

```bash
gh run list --workflow=ci.yml --branch main --limit 1
gh run watch <run-id> --exit-status
```

预期：success，约 3～6 分钟，job 名 `Android JVM Tests`（`ci.yml:35-43` 版本校验、`:53-56` 单测）。
失败：修 main，**绝不打 tag**（tag 的 check 与 CI 同源，必红）。

**A7 复跑发版体检**

```bash
bash tool/release_preflight.sh
```

预期：`0 个 FAIL`，含 `PASS 当前 HEAD 的 CI 已全绿`、`PASS 许可快照可解析：…`、`PASS 许可快照含 N 条 androidx 条目（已按 Android 依赖重生成）`；剩余 WARN 应只有「读不到 v2.1.4.1 的 build number（旧 tag 无 version.properties）」和「自 v2.1.4.1 以来 N 条删除/回滚提交」（工作区当天必须干净）。
失败：按 FAIL 修，此时还没打 tag，成本最低。
说明：
- 解释器选择（`:62-73`）会跳过 Windows 应用商店的 `python3` 占位符；若又出现 `Python was not found`，先确认该函数还在。
- **许可门是 2026-11-10 新加的**（`:336-368`）：只跑 `--verify` 不够——它只证明文件能解析，旧的 Flutter 快照也能过（`tool/license_notices/generate_notices.py:558-573`），所以再加一条「快照里必须有 androidx 条目」判是否已重生成。**该门刚加时曾因旧快照如实 FAIL；2026-11-10 重生成后已 PASS**（234 条、124 条 androidx、SHA-256 `41de0ee2…`、守卫 10/10 绿）。发版前若依赖有变，重跑 `--write` 后必须同步 `FlutterAssetsDecouplingGuardTest.kt:74` 钉值。

## 4. 发布当天会看到的「已知 WARN」

| 输出 | 为什么可以继续 |
|---|---|
| `WARN 读不到 v2.1.4.1 的 build number（'+'）` | v2.1.4.1 是 Flutter 时代 tag，没有 `android/version.properties`；版本比较靠 `150+100000=100150 > 已发布 100140`、`3.0.0 > 2.1.4.1` 人工确认 |
| `WARN 自 v2.1.4.1 以来有 N 条删除/回滚提交` | 逐条确认更新日志里没有对应功能的「新增」（成员十 lane） |
| `WARN 工作区有 N 个未提交条目` | 发布当天必须为 0；否则那部分改动不会进包 |
| `WARN 落后 origin/main N 个提交` | 只在合 main 前出现；A2 之后应消失 |
| `WARN main 上最近一次 CI 不是当前 HEAD` | 只在推 main 前出现；A6 绿后应变成 `PASS 当前 HEAD 的 CI 已全绿` |
| GitCode 附件上传慢 / pgyer 步骤失败 | 异步、`continue-on-error`（`android-build.yml:298-306`），不影响交付 |

**许可门已解（2026-11-10）**：旧快照那条 `FAIL 许可快照里没有 androidx 条目` 已消失——重生成后 234 条、androidx 124 条、`flutter_*` 0 条，gzip 38,837 B、SHA-256 `41de0ee2…`，硬门文档的 B6 同步改「已解决」。若发版前依赖有变，重跑 `--write` 并同步钉值，否则 preflight 会重新判红。
