# CNB 平台 NPC Agent 派工手册（Playbook）

> 目标读者：在本仓库工作的任何 AI Agent（以及人类协作者）。
> 来源：基于 CNB 仓库 `Mutx163/qingyukb` 全量 68 个 ISS + 33 个 PR 的真实调用记录（2026-08-31 ~ 09-02）整理，并经用户确认工作流。
> 维护约定：平台机制或用户习惯变化时更新本文件，并同步 `AGENTS.md` 里的指引段。

## 0. 铁律：何时可以动平台（必读）

- **只读查询随时可做，不需要请示**：用 API 查 ISS / PR / 评论 / 合并状态（见 §6）。
- **一切"会动平台"的操作必须等用户明确下令**：在 ISS/PR 发评论（含 @ NPC）、开 ISS、开/改 PR、合并、关单、打标签……用户不叫，就绝不主动执行，也不"顺手帮忙"批量执行。
- 用户下达指令后**逐步执行**：一次只推进一步（例如"执行第 2 步"），完成即汇报结果、附上下一步建议文案，等用户确认再继续。
- 原因：一次 @ 就是一条真实流水线，可能直接产出代码改动和 PR；多 Agent 并行时，未经指令的 @ 会让平台乱套。
- 派工评论的标准做法是**用户在网页评论框输入 @**（会弹出 NPC 选择器）。Agent 代发评论（API POST）能否触发 NPC 尚未验证——若用户要求代发，先在无关测试单验证一次，或把文案给用户粘贴。

## 1. 平台与坐标

- 平台：**CNB（cnb.cool）**，用户口中的 "CMB" 即此平台。
- 本项目 CNB 仓库：`Mutx163/qingyukb`（GitHub 主仓 `Mutx163/mikcb` 双推送的 CNB 侧；NPC 协作发生在 CNB 侧）。
- **NPC 机制**：在 Issue / PR 评论里 @ 一个 NPC，平台为它启动一条流水线；默认只能读代码、写评论；评论里勾选 **「替我上班」开启工作模式** 后才能写代码、推分支、发 PR（需开发者权限）。NPC 以当事人身份**限时/限地/限权**代办，回复通常以 `@cnb.akIWDscTwHA(仓央嘉措)` 开头（这是用户账号）。
- **编号空间共用**：ISS 与 PR 共用一套 #N（例如 #94 是 PR、#95 是 ISS；68 ISS + 33 PR = 最大编号 101）。看到 `#N` 引用先分清是哪类，再谈对账。

## 2. Agent 花名册与调用语法

| 调用写法 | 角色定位 |
|---|---|
| `@npc/CodeBuddy(glm-5.3-flash)` | **主力**：观点聚合、执行实现、审核汇总、批量开 ISS。⚠️ 是**免费**的 flash 版，**不要用 glm-5.3 标准版** |
| `@npc/CodeBuddy(deepseek-v4-flash)` | 免费智囊：独立讨论 / 独立审核 |
| `@npc/CodeBuddy(hy4-preview)` | 免费智囊：独立讨论 / 独立审核 / 交叉验证 |
| `@CodeBuddy` | 系统内置 NPC（历史上用于 [security] CVE 单的逐条分析） |

语法要点（全部来自真实踩坑记录）：

- 自定义 NPC 通用格式是 `@仓库路径(角色名)`；这里的角色仓库是 `npc/CodeBuddy`，**括号里是模型名**。
- 括号内必须与角色名**完全一致、不能有空格**——曾因 `@npc/CodeBuddy(glm-5.3-flash )` 多一个空格而没触发，只能重发。
- 一条评论可以**连 @ 多个 NPC** 并行派工。
- **空 @**（只发 `@npc/CodeBuddy(glm-5.3-flash)` 不带正文）= "按本 ISS 正文任务书执行"，前提是 ISS 正文把背景、结论、验收标准写全。
- NPC 的 PR 分支名多为 `auto/*`、`fix/*`；评审在 PR 评论里进行，结论格式为 **Approve / 需要修改（needs_modification）**。

## 3. 标准工作流（用户钦定 SOP，五步）

适用：需要动手改代码的任务。**全程由用户逐步下达指令，每步只发一条评论**。

| 步骤 | 执行者 | 评论文案模板 |
|---|---|---|
| ① 独立讨论 | 三个免费模型并行 | `@npc/CodeBuddy(hy4-preview) @npc/CodeBuddy(deepseek-v4-flash) @npc/CodeBuddy(glm-5.3-flash) 开始头脑风暴，根据目前已知内容提出自己的想法不要修改任何东西` |
| ② 观点聚合 | glm-5.3-flash | `@npc/CodeBuddy(glm-5.3-flash) 请总结本页其他 Agent 已发表的意见：归纳共识与分歧点，再补充你自己的判断与建议。` |
| ③ 执行与输出 | glm-5.3-flash | `@npc/CodeBuddy(glm-5.3-flash) 请按照上面的讨论结论直接开工实现，完成后在独立分支提出 PR，并附上验证结果。` |
| ④ 独立审核 | 三个免费模型并行 | `@npc/CodeBuddy(hy4-preview) @npc/CodeBuddy(deepseek-v4-flash) @npc/CodeBuddy(glm-5.3-flash) 独立审核 PR #N，各自给出结论：Approve 或 需要修改（列明问题与位置）` |
| ⑤ 汇总与合并 | glm-5.3-flash → 用户 | `@npc/CodeBuddy(glm-5.3-flash) 请汇总三方审核结论：哪些必须改、哪些可选；如需修改直接修好并推送，然后报告是否可以合并。` |

第 ⑤ 步的分支逻辑：

- **(a)** glm-5.3-flash 汇总三方审核结论；
- **(b)** 审核出必须修改的点 → 由 glm-5.3-flash 修改并推送，必要时回到第 ④ 步复审；
- **(c)** 三方结论基本一致、认为不需要过多修改 → **合并 PR**。合并历来由**用户**在网页操作（历史 merged_by 均为用户本人）；Agent 汇总后应明确报告"可以合并"，等用户合并；除非用户明确授权，Agent 不执行合并。

流程一览：三模型独立讨论 → GLM flash 聚合 → GLM flash 实现（出 PR）→ 三模型独立审核 → GLM flash 汇总 →（需改则改，可复审）/（共识则用户合并 PR，随后关闭对应 ISS）。

## 4. 其它常用派工句式（历史验证有效）

- **交叉验证**：`@npc/CodeBuddy(hy4-preview) 确认结论真实性`
- **让 Agent 反向开单**：`把所有的可选建议和能改的、能做的，你全部开成ISS，我来决定要不要执行 @npc/CodeBuddy(glm-5.3-flash)`
- **批量任务书**：让 NPC 把方案整理成 N 个带标签的 Issue（历史产出：体检①–⑨、架构解耦①–⑤、统计页优化批次），之后在每张单里空 @ 即开工。
- **追问状态 / 续做**：`是失败了还是成功了？做到做完了吗？`、`继续做`
- **条件授权（先答疑再动手）**：`修完这个，不会导致 XX 吧？如果没问题的话，就修一下，然后给我提pr`
- **打包**：`你打一个XXXX版本的软件出来`（走 tag_push 流水线；NPC 推 tag 需要权限时用户先放开限制）。

## 5. 平台卫生习惯

- **PR 合并后关闭对应 ISS**；历史出现过"PR 已合并、ISS 忘关"（2026-09-03 对账发现 #10、#53、#78、#82 四张）。
- 孪生重复单只保留一张跟踪（NPC 开批次单时偶尔开两遍，关一张标注重复）。
- ISS 正文即任务书：背景、已定结论、验收标准写全，空 @ 才能直接开工。
- 评审意见落在 PR 评论里，Agent 之间会互相 @ 复核；保持"结论 + 证据（文件/行号/diff）"的格式。

## 6. Agent 自查用 API 速查（只读，随时可用）

- 助手脚本：`cnb-api "<路径>"`（在 `~/bin/cnb-api`，自动从凭据管理器取令牌；详见 AGENTS.md「CNB API 调用」节）。
- ISS 列表：`/-/issues?state=open` 与 `?state=closed`（**没有 state=all，传了报 400**；要全量就两边拉完合并）。
- 评论：`/-/issues/{n}/comments`、`/-/pulls/{n}/comments`；列表/评论**每页 10 条**，`&page=N` 翻页。
- PR 详情：`/-/pulls/{n}` → 用 `is_merged` / `merged_by` 判断是否真的合并（**state=closed ≠ merged**）。
- ISS↔PR 对账方法：双向引用（ISS 评论里报的 PR 号 ↔ PR 标题/正文/评论里挂的 ISS 号）+ 编号空间归类 + 语境复核剔除顺带提及。
