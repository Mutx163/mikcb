## 0. 一句话结论

官方 demo 里每个组件都给了**正确配方**；我们只抄了组件的「壳」，没抄「配方」。
五条最贵的发现，全部是「官方本来就给了、我们没用」：

| # | 发现 | 官方怎么做的 | 我们怎么做的 | 代价 |
|---|---|---|---|---|
| 1 | **字阶** | `style = MiuixTheme.textStyles.X` | 硬写 `fontSize = N.sp` **577 处** | 14 种随手字号，脱离设计刻度 → 廉价感主因 |
| 2 | **交互反馈** | `pressFeedbackType = Sink` + `showIndication = true` | 一处都没开（0 处） | 点下去没反应 → 「点击效果不好」 |
| 3 | **计划文档里的事实错误** | Scaffold **有** `snackbarHost` 槽 | 计划书写「官方 Scaffold 无 snackbarHost 槽」，让人包一层 | 为一个不存在的问题做设计 |

| 5 | **假实现 + 不实文案** | 真 `textureBlur` 采样背景 | showcase 用主色 alpha 冒充模糊，文案却写「背景捕获 + 高斯模糊」 | 演示页在骗人，违反文案纪律 |

## 1. 发现一：字阶 —— 我们转录了官方字阶，然后绕开它

### 事实

`QingyuTypography`（`android/app/src/main/kotlin/com/mutx163/qingyu/theme/QingyuTypography.kt`）
自称转录自 miuix 的 `defaultTextStyles`。实测**转录得完全正确**，与官方默认值一字不差：

| 槽位 | miuix 默认（`TextStyles.kt:146-238`） | QingyuTypography | 一致 |
|---|---|---|---|
| main | 17sp | `MAIN = 17.0` | ✅ |
| paragraph | 17sp / lineHeight 1.2em | `PARAGRAPH = 17.0` / `1.2` | ✅ |
| body1 | 16sp | `BODY1 = 16.0` | ✅ |
| body2 | 14sp | `BODY2 = 14.0` | ✅ |
| button | 17sp | `BUTTON = 17.0` | ✅ |
| footnote1 | 13sp | `FOOTNOTE1 = 13.0` | ✅ |
| footnote2 | 11sp | `FOOTNOTE2 = 11.0` | ✅ |
| headline1 | 17sp | `HEADLINE1 = 17.0` | ✅ |
| headline2 | 16sp | `HEADLINE2 = 16.0` | ✅ |
| subtitle | 14sp + **Bold** | `SUBTITLE = 14.0`（**漏了字重**） | ⚠️ 唯一不一致 |
| title1/2/3/4 | 32 / 24 / 20 / 18sp | 同 | ✅ |

**也就是说：`QingyuTypography` 是官方默认值的冗余副本，本来白拿。**

### 但我们两边都没用上

```
composeP1 全目录（66 个 .kt）：
  style = MiuixTheme.textStyles.X   0 处
  fontSize = N.sp                 577 处
```

官方 demo 同一口径：`textStyles` **38 处** vs `fontSize` **16 处**——**官方以字阶为主，裸字号是例外**。

### 为什么这直接造成「廉价感」

`MiuixTheme` 的 `Text` 默认 `style = MiuixTheme.textStyles.main`（见官方 `text.md` 属性表）。
一旦显式传 `fontSize`，就**整体覆盖**掉主题样式——包括 `fontFamily`、`fontWeight`、
`lineHeight` 这些主题里统一好的东西。于是：

1. 每个 `Text` 各写各的号 → 实测出现 **14 种字号**（10/11/12/13/14/15/16/17/18/20/22/24/28），
   其中 **10、15、22、28 根本不在官方刻度里**，是各批自己发明的；
2. 主题的字族 / 用户字重 scope（`app_fonts.dart` 那套）**挂不上**，因为字号绕过了样式表；
3. 同一个 App 里字号随机 → 视觉上不成体系，这正是「不像一套东西」的机械原因。

### 修法（最便宜的一刀）

```kotlin
// ❌ 现在（577 处）
Text(text = title, fontSize = 16.sp, fontWeight = FontWeight.Medium, color = ...)

// ✅ 官方配方
Text(text = title, style = MiuixTheme.textStyles.body1, color = MiuixTheme.colorScheme.onSurface)
```

配套：把用户字重 / 字族通过 `MiuixTheme(textStyles = ...)` 一次性注入
（官方 demo 就是这么做的：`ui/Theme.kt` 的 `AppTheme` 收 `textStyles` 参数，
默认 `MiuixTheme.textStyles`，再用 `TextStyles.withFontFamily(fontFamily)` 展开）。
我们现在 `QingyuPageTheme` **只传了 `controller`，没传 `textStyles`**——这是缺口。

`QingyuTypography` 可以保留作为「语义别名 → 槽位名」的映射表（`sizeFor()` 已有这用途），
但**不该再往页面里搬数值**。

## 2. 发现二：交互反馈 —— 官方默认全关，必须显式开

### 事实（官方源码）

`Card.kt:87-95` 两个参数默认关闭：

```kotlin
pressFeedbackType: PressFeedbackType = PressFeedbackType.None,   // 默认无反馈
showIndication: Boolean = false,                                  // 默认无指示
```

官方 `card.md` 的「Interactive Card」一节给的配方是**两个都要显式开**：

```kotlin
Card(
    pressFeedbackType = PressFeedbackType.Sink,
    showIndication = true,
    onClick = { /* ... */ },
)
```

`PressFeedbackType` 三档（`utils/PressFeedback.kt:176`）：`None` / `Sink`（下沉缩放）/
`Tilt`（倾斜）。另有 `holdDownState` 用于「长按期间保持按下态」。

### 我们的现状

```
pressFeedbackType   0 处
PressFeedbackType   0 处
showIndication      0 处
holdDownState       0 处
```

官方 `Card(` 我们调了 **213 次**，其中约 **32 次**传了 `onClick`——**这 32 个可点卡片按下去零反应**。

### 旧版 Flutter 本来是有手感的（对照）

`lib/ui/hyperos/widgets/tiles.dart:45` 起，921 行手写按压状态机：
25ms 出压痕（`_highlightDelay`）、纵向滑动 2dp 取消（`_verticalCancelSlop`）、
翻页期间保持高亮、滚动时重置。`hyperos_controls.dart:784,907` 还有
`HapticFeedback.lightImpact()` 轻震（全仓 27 处）。

**迁到 Compose 后这一层整个没搬**——这就是「点击效果不好」的全部原因，不是 miuix 的锅。

### 修法

**不要逐页补**。建一个 `QingyuCard`（或 `Modifier.qingyuPressable()`）收口：
默认开 `Sink`、圆角按语义给（设置组 24dp / 卡片 16dp）、内边距走 token，
再把 213 处调用换成它。改一处，全站受益。

## 3. 发现三：计划文档里有一条事实错误

`docs/plans/2026-10-26-compose-miuix-components.md:33` 写着：

> ③ Snackbar 统一入口（**官方 Scaffold 无 snackbarHost 槽**）

**实际是错的。** 本地依赖源码：

- `Scaffold.kt:87` — `snackbarHost: @Composable () -> Unit = {}`（槽位存在）
- `Scaffold.kt:88` — `popupHost: @Composable () -> Unit = { MiuixPopupHost() }`（默认已注入）
- `Snackbar.kt` — 官方**提供** `SnackbarHost` / `Snackbar` / `SnackbarHostState.showSnackbar`
- 官方 demo `AppContent.kt:396` 就是这么用的：`snackbarHost = { SnackbarHost(state = snackbarHostState) }`

后果：计划书让人「包一层统一入口」去解决一个不存在的问题；实际全仓 `Snackbar` 命中 **0 处**，
说明这层也没人建——**坑挖了，没填，还挡住了正确做法**。

> ⚠️ 教训：**选型文档里的 API 断言必须对着源码或 demo 核一遍再写进计划。**
> 这份 `compose-miuix-components.md` 是子代理调研产出、Lead 归档的，
> 当时没核对源码就分发给了 22 个批次。同类断言（如「官方 Scaffold 无 xxx」）要全查一遍。

**根因追溯**：官方 `docs/components/scaffold.md:62` 的表格注释本身写着
「Container for displaying Snackbar, **Miuix does not provide this component**」。
这句在 0.9.4 已经过时（`Snackbar.kt` 里 `SnackbarHost` / `Snackbar` /
`SnackbarHostState.showSnackbar` 都在，官方 demo 也这么用）。
计划书作者多半是读了这句，把「不提供 Snackbar 组件」误读成「没有这个槽位」。
**上游文档会过时，凡是「官方没有 X」的结论，必须以本地依赖源码为准。**

## 3.1 发现四：一处半迁移的死代码（会误导下一个人）

`pages/settings/SettingsRowRenderTable.kt` 自称是「渲染层与模型层之间的**字段契约表**」，
但它整段 `Requirement` / `Rendering` / `all` / `rendering()` 机制**没有任何引用**：

```
RenderTable.all           0 处
RenderTable.rendering     0 处
RenderTable.Requirement   0 处
RenderTable.Rendering     0 处
```

只有 `trailingText()` / `colorFromHex()` / `parseArgbOrFallback()` 三个函数在被调用。
也就是说：**这份「契约表」的表格部分早就是死代码**，而它里面写的组件名还是
0.9.4 已整个删除的 `top.yukonga.miuix.kmp.extra.Super*`（见该文件 `:59,64,74,79,84,89`）。

真正在用的是 `SettingsPageModel.kt:49` 的 `MiuixRowComponent`（值已正确迁到
`preference.ArrowPreference` 等），且有 `SettingsRowComponentGuardTest` 守着。
**两份真相源并存，被守的那份是对的，没人守的那份是错的**——而错的那份标题写着
「契约表」，最容易被人当真。

### 修法

删掉 `SettingsRowRenderTable` 里的死机制与 `extra.Super*` 字符串，只留三个真在用的纯函数
（`trailingText` / `colorFromHex` / `parseArgbOrFallback`）并改名去掉「契约表」的暗示；
或者反过来，把 `miuixSymbols` 接进守卫测试。二选一，但**不能让错误的真相源留着**。

## 3.2 发现五：一处「假实现 + 不实文案」

`pages/showcase/MiuixShowcaseSubpages.kt:935-951` 的「模糊 Blur」演示，
实现是**用主色 alpha 冒充模糊**，没有任何背景捕获与高斯模糊
（代码注释自己都写着「模拟模糊卡片预览」）：

```kotlin
Box(
    modifier = Modifier.fillMaxWidth().height(110.dp)
        .clip(RoundedCornerShape(16.dp))
        .background(primaryColor.copy(alpha = (state.blurRadius / 100f).coerceIn(0.15f, 0.85f))),
)
```

而它的文案（`main/.../pages/showcase/ShowcaseStrings.kt:143-146`）声称的是：

> 「MiuixTextureBlur / 液态玻璃（**背景捕获 + 高斯模糊** + 颜色控制）」

**文案与实现不符**——按 AGENTS.md 的 COPY-STYLE 纪律（「不实说明，发现就改」），
这条属于必须改的类型。两条路选一条：把实现补成真模糊（引入 `miuix-blur` 后顺手就对了），
或先把文案改成不含「背景捕获 + 高斯模糊」的描述。**不许留着不一致。**

同类需一起处理：`MiuixShowcaseSubpages.kt:931` 的标题「TextureBlur · 液态玻璃与模糊控制」。

## 4. 官方页面骨架配方（从 demo 直接抄）

官方 `SettingsPage.kt`（设置页）与 `MainPage.kt`（列表页）是离我们最近的骨架。
提炼出的**标准配方**：

```kotlin
Scaffold(
    topBar = {
        BlurredBar(backdrop, blurActive) {          // ① 顶栏毛玻璃（可选但官方默认开）
            AdaptiveTopAppBar(
                title = "标题",
                scrollBehavior = topAppBarScrollBehavior,
                color = barColor,                    // 模糊时传 Color.Transparent
            )
        }
    },
) { innerPadding ->
    Box(modifier = if (backdrop != null) Modifier.layerBackdrop(backdrop) else Modifier) {
        LazyColumn(
            state = lazyListState,
            modifier = Modifier.pageScrollModifiers(...),   // ② 滚动修饰：末端触感 + 过度滚动 + 顶栏联动
            contentPadding = pageContentPadding(innerPadding, padding, isWideScreen),  // ③ 内边距统一算法
        ) {
            item {
                SmallTitle(text = "分组名")                  // ④ 分组标题用官方 SmallTitle，不自绘
                Card(modifier = Modifier.padding(12.dp)) {   // ⑤ 一组设置行用一个 Card 包，**不传 insideMargin**
                    ArrowPreference(title = "...", onClick = {})
                    SwitchPreference(title = "...", checked = x, onCheckedChange = {})
                    // ⑥ 行之间**不加** HorizontalDivider —— 官方 demo 里 Preference 行之间一处都没有
                }
                Spacer(Modifier.height(12.dp))
            }
        }
        VerticalScrollBar(                                   // ⑦ 滚动条是显式挂的
            adapter = rememberScrollBarAdapter(lazyListState),
            modifier = Modifier.align(Alignment.CenterEnd).fillMaxHeight(),
            trackPadding = contentPadding,
        )
    }
}
```

> **关于分割线（2026-10-27 修正）**：官方全 demo 只有 `BlurSection.kt:177/337/492`
> 与 `TextStylePage.kt:124…` 用了 `HorizontalDivider`，**Preference 行之间官方一处都没加**
> （`SettingsPage.kt:120-200` 一整组设置行，行间是干净的）。
> 真要加，照 `BlurSection.kt:177` 的写法带 `padding(horizontal = 16.dp)`，
> 否则线会顶到卡片圆角边上。`scaffold.md` 文档示例里的 `HorizontalDivider()` 是放在
> **裸 LazyColumn**（不在 Card 内）的场景，别照搬进 Card。

> **尺寸刻度（照抄，别自己估）**：页面横向 0（`pageContentPadding` 的 start/end 默认 0）
> → Card 外边距 12 → Preference 自带内边距 16 ⇒ 文字左缘 = 28dp，
> 与 `SmallTitle` 自带的 28dp 对齐。**Card 默认 `insideMargin` 是 `PaddingValues(0.dp)`**，
> 所以包**非 Preference** 的普通内容时必须自己给 `PaddingValues(16.dp)`，
> 包 Preference 行时**不要给**（给了就双重内边距）。
> 这条是「为什么我们的行看起来左右不齐」的直接答案。

### 与我们现状的逐条差异

| 官方做法 | 我们的做法 | 差在哪 |
|---|---|---|
| `SmallTitle(text = "分组")` | 有 42 处用了 `SmallTitle`，另有自绘 `QingyuSectionLabel`（13sp 手写 Text） | 两套并存，自绘那套脱离主题 |
| `Card { Preference 行 }` | `Card { Row { Text } }` 手拼 | 丢掉官方行的内边距 / 按压 / 语义 |
| `ArrowPreference` / `SwitchPreference` | 用了（16 / 11 处），但大量行仍是手拼 | 覆盖率不足 |
| `VerticalScrollBar` 显式挂 | 未用 | 缺滚动条 |
| `pageContentPadding(...)` 统一算内边距 | 各页自己 `padding(...)` | 内边距不一致 |
| `Modifier.pageScrollModifiers(...)` | 未用 | 缺末端触感、过度滚动效果 |

## 6. 给后续 agent 的硬规矩

1. **改任何一页之前**，先在 `docs/reference/miuix-demo/docs/components/<组件>.md` 查官方属性表，
   再到 `example/.../component/<X>Section.kt` 看官方**实际怎么调**。两者冲突以 demo 为准。
2. **不许再往页面里写裸 `fontSize` / 裸 `dp` 圆角**。用 `MiuixTheme.textStyles` 与 `QingyuShapes`。
   确需例外，先在本文件 §5 的清单里登记理由。
3. **任何「官方没有 xxx」的断言，必须贴出源码出处（`文件:行号`）才能写进计划文档。**
4. 官方 demo 是 vendored 只读副本：`docs/reference/miuix-demo/` 下的上游文件一律不改，
   笔记写在本目录的 `CHEATSHEET-*.md` 与本文。
