# 2026-04-05 qingyu_warehouse 教务导入接入方案

## 目标

让轻屿课表（mikcb）能够接入 `qingyu_warehouse` 作为教务适配资源仓，逐步实现：

1. 识别并拉取仓库索引
2. 展示学校 / 工具适配入口
3. 下载并执行适配脚本
4. 将解析后的课程数据映射为轻屿课表内部课程模型
5. 在安全可控的前提下支持后续扩展与多仓兼容

---

## 总体设计

推荐拆成 5 层：

### 1. 仓库协议兼容层
负责拉取并解析：

- `index/root_index.yaml`
- `resources/<folder>/adapters.yaml`
- 对应 `*.js` 脚本资源

输出统一的资源索引模型，供 App UI 和执行层使用。

### 2. 适配资源管理层
负责：

- 仓库地址配置
- 分支 / 版本管理
- 资源缓存
- 资源更新检查
- 回退到本地缓存

### 3. 脚本执行层
负责：

- 执行远程 / 缓存脚本
- 暴露受控 API 给脚本
- 返回标准化导入结果

建议必须做沙箱与权限边界控制，避免脚本拿到不必要的系统能力。

### 4. 登录与导入交互层
负责：

- 学校选择
- 登录入口展示
- WebView / 登录态承载
- 失败重试与错误提示
- 导入确认页

### 5. 数据映射层
负责把脚本返回的数据转换成轻屿课表当前模型，重点处理：

- 课程名 / 老师 / 地点
- 周次 / 自定义周 / 单双周
- 节次 / 时间模板适配
- 多课表归属

---

## 建议开发顺序

## 阶段 1：读仓库，不执行脚本

### 目标
先打通仓库资源链路。

### 交付
- 新增 `WarehouseRepositoryService`
- 能从自定义仓库地址拉取 `root_index.yaml`
- 能列出学校 / 工具条目
- 能读取对应 `adapters.yaml`

### 验证
- 能读取 `qingyu_warehouse`
- 断网时可读取最近缓存

---

## 阶段 2：定义脚本执行协议

### 目标
先统一 App 与脚本之间的输入输出，不急着兼容所有学校。

### 建议输出模型
脚本最终应返回统一结构，例如：

- schoolId
- adapterId
- termInfo
- courses[]
- warnings[]

每门课程至少包含：

- name
- teacher
- location
- dayOfWeek
- startSection
- endSection
- weeks / parity / customWeeks
- startTime / endTime（可选，若仓库只给节次则后续映射）

### 风险
- 上游脚本返回结构可能不完全一致
- 需要加一层标准化转换

---

## 阶段 3：先支持单仓 + 少量学校

### 目标
不要一上来做“全学校兼容”，先挑 1~2 个可验证学校打通闭环。

### 建议
优先选：
- 登录简单
- 数据结构稳定
- 无复杂验证码链路

### 交付
- 学校选择页
- 适配器详情页
- 登录进入导入页
- 导入结果预览页

---

## 阶段 4：接入课表数据映射

### 关键点
轻屿课表当前模型支持：

- 多课表
- 时间模板
- 单双周
- 自定义周
- 课程级时间模板覆盖

因此映射层要处理：

1. 只给节次、不给时间的学校
   - 使用当前课表时间模板推导时间
2. 给具体时间的学校
   - 优先保留原始时间，再决定是否生成新时间模板
3. 连续周 / 单双周 / 离散周
   - 标准化到当前 `Course` 模型

### 建议策略
- 默认导入到当前课表
- 如节次数超出当前模板容量，提供：
  - 自动补齐当前模板
  - 复制模板后补齐并绑定当前课表

---

## 阶段 5：安全与扩展

### 必做安全项
- 禁止脚本直接访问本地文件系统
- 禁止脚本调用任意原生接口
- 对可暴露 API 做白名单
- 明确网络请求策略
- 脚本错误必须隔离，不得拖崩主 UI

### 后续扩展项
- 多仓支持（官方仓 / 自定义仓 / 私有仓）
- 仓库签名或版本校验
- 适配器评分 / 推荐
- 导入日志与诊断

---

## UI 建议

### 入口位置
建议放在：
- 导入课程页面中新增 “教务系统导入”

而不是直接塞进设置页。

### 推荐流程
1. 选择导入方式
2. 选择学校 / 系统
3. 进入登录页
4. 获取并解析课表
5. 预览导入结果
6. 选择导入到哪个课表
7. 处理时间模板与节次冲突
8. 完成导入

---

## 与 qingyu_warehouse 的协作建议

### 仓库侧
- 继续保持与上游 `shiguang_warehouse` 的协议兼容
- 轻屿专用扩展字段要单独记录
- 在 README / CONTRIBUTING 中明确兼容范围

### App 侧
- 优先兼容仓库协议，不硬绑死具体仓库实现
- 支持仓库地址配置，未来可接多源
- 先支持自家 fork，再逐步考虑上游直连兼容

---

## 推荐优先级

### P1
- 仓库索引读取
- 适配器列表展示
- 单仓配置能力
- 导入结果标准模型定义

### P2
- WebView 登录与脚本执行
- 1~2 所学校闭环导入
- 课程映射与冲突处理

### P3
- 多仓支持
- 安全增强
- 仓库版本控制与诊断能力

---

## 当前建议结论

最合适的路线不是“把轻屿课表直接变成上游仓库的绑定客户端”，而是：

- `qingyu_warehouse` 作为轻屿课表的适配资源仓
- `mikcb` 实现仓库协议兼容层 + 执行层 + 数据映射层
- 先完成单仓、单流程、少学校打通，再扩展
